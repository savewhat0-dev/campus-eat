INSTALL / RENDER
1. Back up the repository and PostgreSQL database. Extract this ZIP into the existing Campus Eats project root, preserving paths and replacing the matching files. This is a patch, not a complete project. Existing dependencies, environment variables and all other files remain required.
2. Run npm test, node scripts/menu-import-test.mjs and npm run build:render. Commit the changed files to the GitHub repository connected to your existing Render Web Service.
3. In Render > your Web Service > Environment, add GROQ_API_KEY using a key created at https://console.groq.com/keys. Do not put it in a frontend variable, repository or chat.
   Optional: GROQ_MODEL=openai/gpt-oss-20b
   Optional: CHEF_INPUT_LIMIT=500 (supported range 100–1000)
   Save and redeploy. Keep the existing DATABASE_URL, PUBLIC_ORIGIN, Gmail sender credentials and RETAILER_ACCOUNTS.
4. Deploy the latest commit. Start command remains npm run start:render. The startup migration automatically creates order_payments once (0005_order_payments). Do not delete or recreate the database.
5. Check /healthz, sign-in, Chef, an actual retailer's outlet, and a sample order on the live deployment before campus rollout. This local patch has not been deployed to Render.

GROQ
The key stays on the Node server. Groq classifies the food request into a constrained intent/query; its prose is never shown. Product cards, prices and availability are obtained from the server's catalog. No customer profiles, other people's orders, retailer data or API credentials are sent as model context. Greetings, clarification, campus-food scope, message length and rate limits are enforced. Without a configured key, the existing menu assistant remains available; that fallback does not call Groq. Actual Groq delivery was not tested because no live key was supplied.
Official model reference checked: https://console.groq.com/docs/models

SESSIONS / BACK
Sessions use HttpOnly cookies with a 30-day lifetime, Secure on HTTPS, SameSite=Strict, and renewal on authenticated return visits. Refresh, navigation and temporary network failures do not deliberately log users out. Logout revokes the server session; true expiry opens sign-in while retaining the bag and navigation context. Retailer tabs are remembered in sessionStorage, with no credentials stored there. Product/overlay Back, outlet Back, Chef Back and retailer editor/tab Back were checked in the browser. Root Back retains normal browser behavior.

READY-STAGE PAYMENTS
Ready and unpaid orders show Pay now and Pay at pickup. The preference persists in PostgreSQL. Pay now opens an inline panel with the outlet, reference and amount. Default display is explicitly "Demo QR — payments not enabled". Scanning, opening a QR or collecting an order never records a payment. Only the signed-in retailer assigned to the outlet can record full receipt; duplicate confirmations are rejected. Receipt is stored separately from preparation/collection and appears in received-money reporting.
The uploaded QR has not been activated because its payee and outlet assignment were not verified. Do not use it for multiple outlets without confirmation.
Optional actual-QR setup: after independently verifying the payee and correct outlet, save an image under public/assets/payments/, and set PAYMENT_QR_BY_OUTLET to a JSON mapping such as {"kathi":{"verified":true,"path":"/assets/payments/kathi.png"}}. Only permitted local image paths for that outlet are returned to its order owner. Omitting the setting keeps demo mode. There is no payment gateway, automatic charge, scan-based payment confirmation or new refund workflow.
